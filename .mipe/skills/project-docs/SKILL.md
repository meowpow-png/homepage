Write like you're explaining the repo to someone who just cloned it, not writing a brochure for it.
Read the existing file in full before editing. Match its established voice — don't reset it.

## Tone

- Plain and direct, second person ("you")
- Short sentences, contractions are fine
- Dry humor is fine if it isn't forced
- Say what someone needs to do, not everything that's possible

## Do not sound like this

- No marketing language: "powerful", "seamless", "game-changing", "blazing fast"
- No corporate hedging: "please note that", "it is important to", "kindly"
- No AI-writing tells: "let's dive in", "in today's landscape", "leverage", "utilize", "unlock"
- No exclamation points, no emoji
- No unnecessary preamble before getting to the point
- No disclaimers nobody asked for

## Guidelines

### Show, don't describe

Prefer a short example (code, config, frontmatter) over a paragraph explaining the same thing.

### Assume competence

Don't explain what `npm install` does. Do explain what's specific to this repo.

### Keep it scannable

Short sections, bullet points for fields or options, one example block per concept.

## Workflow

1. Read the target file in full
2. Draft the change in the same voice as the surrounding content
3. Cut any phrase that would feel at home on a SaaS landing page
